# Project status

Last updated: 2026-10-19 (B4a released to `main` through PR #46 and release PR #47, `58cead5`, not deployed; B4b inquiry console built and tested on `admin`, PR `admin` to `staging` for owner review, not merged, not deployed).

## In one paragraph

The public website (frontend) is built, bilingual (Indonesian at `/`, English at `/en/`), prerendered as static HTML, and released to `main`. The Laravel 13 backend exposes `POST /api/v1/inquiries` and `GET /up` on **PHP 8.5 (at least 8.5.7)** and **MySQL 8.4 LTS**. Since B2.1 the inquiry endpoint is **idempotent per `Idempotency-Key`**, and since B2.2 the website client sends one key per logical submission and lets the visitor check an unconfirmed attempt with the same key. The contact form's **Send through website** channel (B2) is built but **disabled by default** (`VITE_INQUIRY_API_ENABLED=false`), so shipped builds never call the API. The repository now has a **full-Docker development environment** (`infra/docker/compose.dev.yaml`, reusing the existing MySQL container) and a **production-oriented Docker configuration** (`infra/docker/compose.prod.yaml`): production Docker configuration prepared and validated, **not publicly deployed**. No domain, hosting, certificate, or production database exists. Since B3.1a (released to `main` in PR #33, merge `ffe07fc`) the backend also holds the **admin identity core** under `/api/v1/admin`: owner bootstrap on the shell, single-use access links, mandatory TOTP before activation, database sessions, roles `owner` and `admin`, and an append-only audit log. Since B3.1b (released to `main` in PR #35, merge `4874c73`) owners also have an API for user administration and audit reading: invitations shown once and delivered by hand, role changes, suspension, owner-issued credential reset, and an owner-only audit reader. No admin account exists anywhere. The admin application (`admin/`) has its foundation (B3.2a, PR #38), sign-in, access-link activation and reset, and own-account security (B3.2b, PR #41), and the owner administration workspace (B3.2c, PR #43) released to `main`. B3.2d (released to `main` in PR #45, `eb31fae`) adds the **production admin image and the private admin listener** (`admin-gateway`, Compose profile `admin`, loopback by default, optional TLS in the listener), validated end to end in Docker CI with synthetic data and a throwaway certificate; **not deployed**: no admin hostname, certificate, or account exists. Since B4a (released to `main` in PR #47, `58cead5`) the backend also holds the **inquiry management API** for owner and admin (masked contacts, status workflow with history, append-only notes, a deliberate and recorded contact reveal; `docs/api/admin-inquiries.md`); since B4b (built and tested on `admin`, **not released, not deployed**) the console has the **inquiry screens** on it (list with indexed filters, detail, compare-and-set status changes, append-only notes, the deliberate password-confirmed contact reveal, `inquiry.*` audit labels), and export, deletion, and retention wait for owner decisions. Deploying the admin, releasing B4b, visitor analytics, and the GitHub integration boundary are not built (`docs/architecture/`). Supported coding agents: Claude Code and Codex.

- **Security fix (backend, owner decision 2026-10-17: fix in this PR):** a TOTP code from the next 30-second step could be used twice, in another session, because Fortify's replay cache stored the current step instead of the matched one (google2fa answers `true` when no earlier use is passed). Found by the first **Admin integration** CI run on PR #39, reproduced locally and in PHPUnit. `App\Services\ReplaySafeTwoFactorAuthenticationProvider`, bound in `FortifyServiceProvider`, caches the matched step for the code's whole validity (90 s); regression test `AdminSignInTest::test_a_totp_code_from_the_next_step_cannot_be_replayed` (mutation-checked). Applies to sign-in and enrollment confirmation.
- **TOTP replay hardening (security review after PR #39, 2026-10-18):** two more flaws in the replay cache, both reproduced on the real MySQL testing database and present in stock Fortify 1.41 too. (1) The key was `md5(code)` alone, so another account's use of the same six digits rejected a person's own valid code (a same-step collision pair was found by search; account B refused after account A). (2) Read, verify, and write were separate, so two simultaneous verifications of one code both succeeded: 20 of 20 rounds in two PHP processes with their own MySQL connections (stock Fortify 10 of 10). Now a code is accepted only by an atomic `add` claim on (authenticator, matched step) on the `database` cache store whatever `CACHE_STORE` says, keyed by an HMAC of secret and step from an `APP_KEY`-derived key (no code, secret, or account data in the cache), lasting 120 s (validity 90 s, drift window unchanged); the provider refuses a store without an atomic shared `add`. After the fix: 20 of 20 rounds exactly one acceptance. Tests: `TotpReplayProtectionTest` (10, pinned steps, exact boundaries, claim lifetime, collision pair, key contents, store refusal) and `TotpReplayConcurrencyTest` (two processes through the container binding, and two sessions on two Laravel servers over real HTTP aligned by a test-only barrier in `backend/tests/E2E/server.php`); with stock Fortify bound, both concurrency tests fail.

## B2.2: inquiry idempotency and safe retry (frontend)

- One `LogicalSubmission` (key from `crypto.randomUUID()` plus the canonical values sent with it) per website submission, in component memory only. Same canonical content reuses the key (also after edit and restore); other content gets a new key. No fallback generator: without Web Crypto (old browser, or plain HTTP to a LAN IP) nothing is sent and WhatsApp or email is suggested.
- Retired after `201`, `400`, `409`; kept after uncertain outcomes and after refusals that do not use up the key. No automatic retry at all: an uncertain result shows **Kirim ulang permintaan yang sama** / **Retry the same request** while the content is unchanged, and explains that changed content becomes a separate request.

- Known limitation (deliberate): a reload, closed tab, or navigation forgets the key, so a resend after that can create a second inquiry. Persisting it would put personal data in browser storage.
