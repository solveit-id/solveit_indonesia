# Project status

## In one paragraph

The public website (frontend) is built, bilingual (Indonesian at `/`, English at `/en/`), prerendered as static HTML, and released to `main`. The Laravel 13 backend exposes `POST /api/v1/inquiries` and `GET /up` on **PHP 8.5 (at least 8.5.7)** and **MySQL 8.4 LTS**. Since B2.1 the inquiry endpoint is **idempotent per `Idempotency-Key`**, and since B2.2 the website client sends one key per logical submission and lets the visitor check an unconfirmed attempt with the same key. The contact form's **Send through website** channel (B2) is built but **disabled by default** (`VITE_INQUIRY_API_ENABLED=false`), so shipped builds never call the API. The repository now has a **full-Docker development environment** (`infra/docker/compose.dev.yaml`, reusing the existing MySQL container) and a **production-oriented Docker configuration** (`infra/docker/compose.prod.yaml`): production Docker configuration prepared and validated, **not publicly deployed**. No domain, hosting, certificate, or production database exists. Since B3.1a (released to `main` in PR #33, merge `ffe07fc`) the backend also holds the **admin identity core** under `/api/v1/admin`: owner bootstrap on the shell, single-use access links, mandatory TOTP before activation, database sessions, roles `owner` and `admin`, and an append-only audit log. Since B3.1b (released to `main` in PR #35, merge `4874c73`) owners also have an API for user administration and audit reading: invitations shown once and delivered by hand, role changes, suspension, owner-issued credential reset, and an owner-only audit reader. No admin account or admin listener exists anywhere. The admin application (`admin/`) has its foundation (B3.2a, PR #38) and sign-in, access-link activation and reset, and own-account security (B3.2b, PR #41) released to `main`, and on the `admin` branch the owner administration workspace (B3.2c: users, account detail with role change, suspension, reactivation, and credential reset, invitations, audit log; under owner review); it is not deployed. The private admin release (B3.2d), inquiry management (B4), visitor analytics, and the GitHub integration boundary are not built (`docs/architecture/`). Supported coding agents: Claude Code and Codex.

- **Session state:** in memory only (`src/auth/session.ts`), filled only from a verified `GET me` or the account returned by `access-links/confirm`, emptied on any 401, on sign-out, and when another tab of the browser signs out (`BroadcastChannel`, facts only, no data). The page is hidden and re-checked after the tab was hidden 60 s or more, after the device slept, and after a back-forward-cache restore. Idle warning (WCAG 2.2.1) five minutes before the expected 30-minute expiry, estimated from the last response that reached the session; "stay signed in" is one real `GET me`; at the expected expiry one `GET me` checks and a 401 leads to sign-in. Notice ten minutes before the 12-hour limit, without extension. No polling.
- **Sign-in:** password, then TOTP or a recovery code; generic answer for every login refusal; `autocomplete` username, current-password, one-time-code; paste allowed; values cleared once sent. The exact "sign-in attempt has expired" answer (also after the client's one 419 replay) returns to the password step instead of "wrong code". 409 verifies and enters; 429 shows a bounded countdown (Retry-After, at most an hour) and sends nothing meanwhile; uncertain outcomes are never resent, the challenge offers a read-only session check.
- **Access links:** the token is taken from the fragment in `main.tsx` before the router starts, removed from the address and history, held in the access screen's memory only, and dropped once the link is used or refused. Inspect on arrival (does not use the link), redeem only on submit, masked address and expiry from Laravel, name only for activation, 12 characters and 72 bytes checked before sending, credential reset explains that the old authenticator and codes already stopped working. 409 offers sign-out and re-inspects the same link; an uncertain redeem offers "check the link" instead of a resend.
- **TOTP enrollment and recovery codes:** QR as `<img src="data:image/svg+xml,...">` (never injected markup; only SVG documents accepted), setup key in groups of four with an explicit copy button, deadline from `confirm_before`. Confirmation verifies the account, then shows the codes once with explicit copy and a required acknowledgement; in-app navigation is blocked and reload/close warned until then. Nothing is stored or refetched; an uncertain confirmation is resolved by a read (`GET me`) and, if the account became active, points to regenerating codes.
- **Own account:** `/akun` read-only (no profile API). `/akun/keamanan`: password change (sessions list and account refreshed afterwards), recovery-code regeneration (confirm, then on 423 the password dialog, then a second deliberate decision, never in the background), sessions listed with opaque handles never shown, end one or all others after confirmation, uncertain results never repeated.
- **API client:** typed endpoints (`src/services/admin-api/account.ts`) with the 419 policy per call: only the five allowlisted authentication steps replay; redeem, confirm, password, recovery codes, and sessions stay `confirm`. A response observer reports statuses only, for idle tracking.
- **Real-browser harness:** `backend/tests/E2E/` (safety gate on every command and every HTTP request: APP_ENV must be unset or testing, pinned values like `phpunit.xml`, then `TestDatabaseGuard`; a test-only clock offset for Laravel; the PHP built-in server with a gated router; `reset` truncates the testing database between tests) and `admin/tests/integration/` (Playwright against the production build on `127.0.0.1:4176` and Laravel on `127.0.0.1:8100`, real TOTP in Node, links from the real `admin:bootstrap-owner` and `admin:reset-credentials` commands and owner invitations, no traces, screenshots, or videos). CI: `.github/workflows/admin-integration.yml` with a disposable MySQL 8.4.
- **Security fix (backend, owner decision 2026-10-17: fix in this PR):** a TOTP code from the next 30-second step could be used twice, in another session, because Fortify's replay cache stored the current step instead of the matched one (google2fa answers `true` when no earlier use is passed). Found by the first **Admin integration** CI run on PR #39, reproduced locally and in PHPUnit. `App\Services\ReplaySafeTwoFactorAuthenticationProvider`, bound in `FortifyServiceProvider`, caches the matched step for the code's whole validity (90 s); regression test `AdminSignInTest::test_a_totp_code_from_the_next_step_cannot_be_replayed` (mutation-checked). Applies to sign-in and enrollment confirmation.
- **TOTP replay hardening (security review after PR #39, 2026-10-18):** two more flaws in the replay cache, both reproduced on the real MySQL testing database and present in stock Fortify 1.41 too. (1) The key was `md5(code)` alone, so another account's use of the same six digits rejected a person's own valid code (a same-step collision pair was found by search; account B refused after account A). (2) Read, verify, and write were separate, so two simultaneous verifications of one code both succeeded: 20 of 20 rounds in two PHP processes with their own MySQL connections (stock Fortify 10 of 10). Now a code is accepted only by an atomic `add` claim on (authenticator, matched step) on the `database` cache store whatever `CACHE_STORE` says, keyed by an HMAC of secret and step from an `APP_KEY`-derived key (no code, secret, or account data in the cache), lasting 120 s (validity 90 s, drift window unchanged); the provider refuses a store without an atomic shared `add`. After the fix: 20 of 20 rounds exactly one acceptance. Tests: `TotpReplayProtectionTest` (10, pinned steps, exact boundaries, claim lifetime, collision pair, key contents, store refusal) and `TotpReplayConcurrencyTest` (two processes through the container binding, and two sessions on two Laravel servers over real HTTP aligned by a test-only barrier in `backend/tests/E2E/server.php`); with stock Fortify bound, both concurrency tests fail.
- **Console fix from the PR #40 CI (B3.2b):** the idle warning could loop `GET me` without end when its estimate of the 12-hour deadline was already past but Laravel still answered 200 (exposed when the calendar passed a fixed test-fixture date and Docker CI hung on the admin unit tests). A passed deadline is now checked once; Laravel's clock then decides. Regression test in `src/app/idle-warning.test.tsx`, mutation-checked; fixtures use 2099.
- **Finding:** Chromium sends `Sec-Fetch-Site: same-origin` on every console request and restores it even when a test removes it, and Laravel's CSRF check accepts that header, so a real browser practically never gets a 419 from this API. The real 419 is proven at the API boundary; the browser test simulates only the first 419 and lets the replay reach real Laravel.
- **Tests:** 256 unit and component tests (136 before), mocked browser suite 97 (desktop 31 plus 2 phone-only skips, tablet 33, mobile 33), real-browser suite 37 (desktop 33, tablet 2, mobile 2). Initial JS 131.0 KB gzip (110.8 before, budget 150).

- **Credential reset:** the target is locked out at once and recovers only with a new password and a new authenticator; a lost, expired, or abandoned link is replaced by issuing again. `admin:reset-credentials` stays the shell emergency path.
- **Audit reader:** owner only, newest first by `id`, filters `action`, `actor_type`, `actor_user_id`, `subject_user_id`, `occurred_from`/`occurred_to` on indexed columns, metadata filtered again by the allowlist, IP and user agent shown to owners. No write, detail, or export endpoint. The append-only triggers are unchanged; they do not protect against DDL holders (`TRUNCATE`, `DROP TRIGGER`), and the production smoke test now checks that `solveit_app` cannot `TRUNCATE`.
- **Session driver:** fixed to `database` in `config/session.php` (no longer read from `SESSION_DRIVER`); the admin API answers `503` without a session if another driver is active at runtime.
- **Tests:** 376 tests, 2,836 assertions (261 and 1,216 at `ffe07fc`), including 57 new admin test methods and 6 multi-process concurrency tests. Production smoke test: all checks pass with 8 new path checks and the `TRUNCATE` refusal.

## B2.1: inquiry idempotency (backend)

Status: Implemented and Tested (locally, in the Docker dev container, and in Backend CI). Not deployed. Used by the website client since B2.2 (below). Contract: `docs/api/inquiries.md`, section Idempotensi (B2.1). Evidence: `docs/qa/qa-report.md`, section B2.1.

- Optional header `Idempotency-Key`: exactly one UUID v4 (any case). Malformed: `400` before validation. Missing: B1 behaviour, no duplicate protection.
- Same key and equivalent canonical payload: `201` with the original reference and `Idempotent-Replayed: true`, no new row. Same key, different content: `409`, nothing stored, no reference revealed. Different keys: independent inquiries.
- Storage: nullable `UNIQUE` column `inquiries.idempotency_key_hash` (SHA-256 of the key, never the key). The insert itself is the check; a losing concurrent insert waits on InnoDB, then replays or conflicts. No second copy or fingerprint of personal data: equivalence compares the stored row. Deadlocks are retried up to three times.
- Failed inserts (`503`) and rejected payloads (`422`) do not consume the key. Rate limiting still counts every retry. CORS allows the header only for the configured origins and exposes `Idempotent-Replayed`.
- Key lifecycle: the hash lives and dies with the inquiry row; no separate expiry (retention is an owner decision).
- Tests: 151 tests, 466 assertions (109 and 275 before), including five multi-process tests with independent MySQL connections and a mutation check that proved they fail without the key hash.

## B2.2: inquiry idempotency and safe retry (frontend)

Status: Implemented and Tested (unit, component, mocked E2E in Chromium and Firefox, and a real browser to Laravel to MySQL 8.4 smoke test with synthetic data). Not deployed; the channel stays **disabled by default** (`VITE_INQUIRY_API_ENABLED=false` in `.env.example`, default builds, and `compose.prod.yaml`). Design: `docs/api/inquiries.md`, section Penerapan di frontend (B2.2). Evidence: `docs/qa/qa-report.md`, section B2.2. Backend, CORS, and Docker unchanged.

- One `LogicalSubmission` (key from `crypto.randomUUID()` plus the canonical values sent with it) per website submission, in component memory only. Same canonical content reuses the key (also after edit and restore); other content gets a new key. No fallback generator: without Web Crypto (old browser, or plain HTTP to a LAN IP) nothing is sent and WhatsApp or email is suggested.
- Retired after `201`, `400`, `409`; kept after uncertain outcomes and after refusals that do not use up the key. No automatic retry at all: an uncertain result shows **Kirim ulang permintaan yang sama** / **Retry the same request** while the content is unchanged, and explains that changed content becomes a separate request.
- Only Laravel's exact `503` body counts as "not stored"; any other `503`, `502`, `504`, `5xx`, unreadable `201`, network error, or timeout is uncertain. `429` blocks new requests until `Retry-After` passes. `Idempotent-Replayed: true` adds one sentence to the normal receipt.
- Known limitation (deliberate): a reload, closed tab, or navigation forgets the key, so a resend after that can create a second inquiry. Persisting it would put personal data in browser storage.
- Tests: 178 unit and component tests (125 before), API-build E2E 15 per project (9 before), default E2E 488 unchanged. Bundle: +866 bytes gzip in total.
