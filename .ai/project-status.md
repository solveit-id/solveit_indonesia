# Project status

Last updated: 2026-10-16 (B3.2a admin console foundation in progress on `admin`; last release B3.1b, PR #35, merge commit `4874c73`).

## In one paragraph

The public website (frontend) is built, bilingual (Indonesian at `/`, English at `/en/`), prerendered as static HTML, and released to `main`. The Laravel 13 backend exposes `POST /api/v1/inquiries` and `GET /up` on **PHP 8.5 (at least 8.5.7)** and **MySQL 8.4 LTS**. Since B2.1 the inquiry endpoint is **idempotent per `Idempotency-Key`**, and since B2.2 the website client sends one key per logical submission and lets the visitor check an unconfirmed attempt with the same key. The contact form's **Send through website** channel (B2) is built but **disabled by default** (`VITE_INQUIRY_API_ENABLED=false`), so shipped builds never call the API. The repository now has a **full-Docker development environment** (`infra/docker/compose.dev.yaml`, reusing the existing MySQL container) and a **production-oriented Docker configuration** (`infra/docker/compose.prod.yaml`): production Docker configuration prepared and validated, **not publicly deployed**. No domain, hosting, certificate, or production database exists. Since B3.1a (released to `main` in PR #33, merge `ffe07fc`) the backend also holds the **admin identity core** under `/api/v1/admin`: owner bootstrap on the shell, single-use access links, mandatory TOTP before activation, database sessions, roles `owner` and `admin`, and an append-only audit log. Since B3.1b (released to `main` in PR #35, merge `4874c73`) owners also have an API for user administration and audit reading: invitations shown once and delivered by hand, role changes, suspension, owner-issued credential reset, and an owner-only audit reader. No admin account or admin listener exists anywhere; the admin application (`admin/`, B3.2a) is being built on the `admin` branch and is not deployed. The admin application and modules, visitor analytics, and the GitHub integration boundary are designs only (`docs/architecture/`). Supported coding agents: Claude Code and Codex.

## B3.1b: owner user administration and audit reader (backend)

Status: Implemented, Tested, and **released to `main`** (PR #34 merged to `staging` as `7105161`, release PR #35 merged as `4874c73`; Backend CI and Docker CI green on both, run IDs below). Backend only, not deployed, no account. Contract: `docs/api/admin-users.md`. Decisions: `docs/architecture/admin-dashboard.md` section 4. Evidence: `docs/qa/qa-report.md`, section B3.1b.

- **Owner decisions (confirmed by the owner on 2026-10-16 at the start of the task):** invitations are never emailed, the raw link appears once in the issuing owner's response and is delivered by hand; only `owner` reads the whole audit log; invitation links last 48 hours, owner-issued reset links 24 hours (shell links stay 30 minutes); audit retention still pending, so no pruning, deletion, or export.
- **Endpoints (11 new, 25 admin routes):** `GET users`, `GET users/{id}`, `PUT users/{id}/role`, `POST`/`DELETE users/{id}/suspension`, `POST users/{id}/credential-reset` (needs `acknowledge_access_loss: true`), `GET`/`POST invitations`, `GET`/`DELETE invitations/{id}`, `GET audit-events`. Cursor pagination (1 to 100, default 25), allowlisted filters, unknown parameters and tampered cursors refused with `422`, `409` errors carry a stable `code`.
- **Authorization:** six new permissions (`users.view`, `users.invite`, `users.change-role`, `users.suspend`, `users.reset-credentials`, `audit.view-all`), granted to `owner` by name, never to `admin`. Each route asks for exactly one; accounts are looked up after the check (no existence oracle). Writes also need password confirmation within 15 minutes (after `can:`) and `admin-administration` (20 per minute).
- **Invariants:** an active owner is one who can sign in (confirmed authenticator). Every owner operation locks the active owners, rechecks the actor under the lock, writes its audit event in the same transaction (an audit failure undoes everything), and retries InnoDB deadlocks (found by the multi-process tests: without the retry two owners demoting each other got a 500). No self role change, suspension, or reset; the last active owner stays. Role change and suspension end the target's sessions; suspension also revokes open links; reactivation creates no session.
- **Invitations:** new account or the pending account with that address (no duplicates); refused for activated, suspended, or role-less accounts and while a live invitation exists. MySQL enforces one open link per account (generated column `admin_access_links.open_for_user_id`, `UNIQUE`, new additive migration). Revocation stops an enrollment already in progress.
- **Credential reset:** the target is locked out at once and recovers only with a new password and a new authenticator; a lost, expired, or abandoned link is replaced by issuing again. `admin:reset-credentials` stays the shell emergency path.
- **Audit reader:** owner only, newest first by `id`, filters `action`, `actor_type`, `actor_user_id`, `subject_user_id`, `occurred_from`/`occurred_to` on indexed columns, metadata filtered again by the allowlist, IP and user agent shown to owners. No write, detail, or export endpoint. The append-only triggers are unchanged; they do not protect against DDL holders (`TRUNCATE`, `DROP TRIGGER`), and the production smoke test now checks that `solveit_app` cannot `TRUNCATE`.
- **Session driver:** fixed to `database` in `config/session.php` (no longer read from `SESSION_DRIVER`); the admin API answers `503` without a session if another driver is active at runtime.
- **Tests:** 376 tests, 2,836 assertions (261 and 1,216 at `ffe07fc`), including 57 new admin test methods and 6 multi-process concurrency tests. Production smoke test: all checks pass with 8 new path checks and the `TRUNCATE` refusal.

## B3.1a: admin identity core (backend)

Status: Implemented, Tested, and **released to `main`** (PR #33, merge commit `ffe07fc`; Backend CI and Docker CI green on PRs #32 and #33). Not deployed, no admin account anywhere. Contract: `docs/api/admin-auth.md`. Architecture and decisions: `docs/architecture/admin-dashboard.md`. Evidence: `docs/qa/qa-report.md`, section B3.1a.

- **Authentication:** Laravel session guard plus Fortify 1.41 as a headless library (`Fortify::ignoreRoutes()`; only the routes in `routes/admin.php` exist). **No Sanctum**: its stateful middleware forces `SameSite=Lax` (verified in v4.3.3 source), and the admin is same-origin. Sessions exist only in the `admin` middleware group; `POST /api/v1/inquiries` and `/up` stay cookie-free (tested); CORS now applies only to `api/v1/inquiries`.
- **Boundary:** `AdminRequestBoundary` (exact host of `ADMIN_URL`, exact `Origin`, no `same-site`/`cross-site` fetches, `Origin` required on writes, `no-store`), `AdminPreventRequestForgery` (Laravel's check without its unit-test bypass). Public gateway listener answers every `/api/v1/admin` spelling with 404.
- **Policy fixed in config:** database sessions, encrypted, host-only `HttpOnly` `SameSite=Strict`, `__Host-` and `Secure` when `ADMIN_URL` is https, idle 30 min, absolute 12 h, password confirmation 15 min, no remember me, session ID regenerated at sign-in.
- **Identity:** `admin:bootstrap-owner` and `admin:reset-credentials` (shell only; link printed once, never stored or logged); links are 256-bit tokens in the URL fragment, stored as SHA-256, single use, one live link per account; activation sets the password and confirms a 160-bit TOTP secret before the account can sign in; identical login failures with a 400 ms timebox; TOTP replay refused; recovery codes consumed; own sessions listed by HMAC handle and revocable; password change ends other sessions. `DatabaseSeeder` no longer creates `test@example.com` with password `password`.
- **Authorization:** roles `owner` and `admin` only, one Gate per permission (`account.manage-own` so far), default deny; `ChangeAdminRole` and `SuspendAdminAccount` (for B3.1b) keep the last active owner, refuse self-changes, and end the target's sessions. Route coverage test classifies every admin route into one tier.
- **Audit:** `admin_audit_events`, allowlisted metadata, no secrets or personal data beyond IP and truncated user agent; model guards plus MySQL `BEFORE UPDATE`/`BEFORE DELETE` triggers for every database user. **Retention is pending an owner decision; nothing prunes.**
- **MySQL setting (owner decision):** `log_bin_trust_function_creators = ON`, needed for non-SUPER users to create triggers under binary logging (error 1419 verified). Set in both `initdb` scripts and Backend CI; applied once on the owner machine with `SET PERSIST` (see below). It is a **server-wide** global variable (it applies to every database and user on that MySQL server), so it is a **production provider prerequisite**: the chosen host or managed MySQL must allow it, preferably on a server dedicated to this website (`backend/README.md`, Trigger audit).
- **Tests:** 261 tests, 1,216 assertions (151 and 466 before), including 110 admin tests through `tests/Support/InteractsWithAdminApi.php` (real cookies, Origin, CSRF, TOTP) and mutation checks for every defence. Production smoke test: 59 checks (33 before).
- **Dependencies added:** `laravel/fortify` ^1.41 (brings `laravel/passkeys`, `web-auth/webauthn-lib`, `pragmarx/google2fa`, `bacon/bacon-qr-code`, and Symfony 8.1 serializer/property-access/property-info/type-info used only by the inactive passkey library). `composer audit` clean.

## B2.1: inquiry idempotency (backend)

Status: Implemented and Tested (locally, in the Docker dev container, and in Backend CI). Not deployed. Used by the website client since B2.2 (below). Contract: `docs/api/inquiries.md`, section Idempotensi (B2.1). Evidence: `docs/qa/qa-report.md`, section B2.1.

- Optional header `Idempotency-Key`: exactly one UUID v4 (any case). Malformed: `400` before validation. Missing: B1 behaviour, no duplicate protection.
- Same key and equivalent canonical payload: `201` with the original reference and `Idempotent-Replayed: true`, no new row. Same key, different content: `409`, nothing stored, no reference revealed. Different keys: independent inquiries.
- Storage: nullable `UNIQUE` column `inquiries.idempotency_key_hash` (SHA-256 of the key, never the key). The insert itself is the check; a losing concurrent insert waits on InnoDB, then replays or conflicts. No second copy or fingerprint of personal data: equivalence compares the stored row. Deadlocks are retried up to three times.
- Failed inserts (`503`) and rejected payloads (`422`) do not consume the key. Rate limiting still counts every retry. CORS allows the header only for the configured origins and exposes `Idempotent-Replayed`.
- Key lifecycle: the hash lives and dies with the inquiry row; no separate expiry (retention is an owner decision).
- Tests: 151 tests, 466 assertions (109 and 275 before), including five multi-process tests with independent MySQL connections and a mutation check that proved they fail without the key hash.

## B2.2: inquiry idempotency and safe retry (frontend)

Status: Implemented and Tested (unit, component, mocked E2E in Chromium and Firefox, and a real browser to Laravel to MySQL 8.4 smoke test with synthetic data). Not deployed; the channel stays **disabled by default** (`VITE_INQUIRY_API_ENABLED=false` in `.env.example`, default builds, and `compose.prod.yaml`). Design: `docs/api/inquiries.md`, section Penerapan di frontend (B2.2). Evidence: `docs/qa/qa-report.md`, section B2.2. Backend, CORS, and Docker unchanged.

- One `LogicalSubmission` (key from `crypto.randomUUID()` plus the canonical values sent with it) per website submission, in component memory only. Same canonical content reuses the key (also after edit and restore); other content gets a new key. No fallback generator: without Web Crypto (old browser, or plain HTTP to a LAN IP) nothing is sent and WhatsApp or email is suggested.
- Retired after `201`, `400`, `409`; kept after uncertain outcomes and after refusals that do not use up the key. No automatic retry at all: an uncertain result shows **Kirim ulang permintaan yang sama** / **Retry the same request** while the content is unchanged, and explains that changed content becomes a separate request.
- Only Laravel's exact `503` body counts as "not stored"; any other `503`, `502`, `504`, `5xx`, unreadable `201`, network error, or timeout is uncertain. `429` blocks new requests until `Retry-After` passes. `Idempotent-Replayed: true` adds one sentence to the normal receipt.
- Known limitation (deliberate): a reload, closed tab, or navigation forgets the key, so a resend after that can create a second inquiry. Persisting it would put personal data in browser storage.
- Tests: 178 unit and component tests (125 before), API-build E2E 15 per project (9 before), default E2E 488 unchanged. Bundle: +866 bytes gzip in total.
